# AGENTS.md

Project rules for AI coding agents. This file is the single source of truth;
`CLAUDE.md` and `.github/copilot-instructions.md` import or point at it rather
than restating it, so the rules cannot drift apart.

## What this is

`@plq/use-persisted-state` — a React hook that persists state to a storage
backend. Published to npm as a library, so every change to `src/` is a change
to a public API that other people depend on.

- Runtime dependency: `@plq/is` only. Keep it that way; the package must stay small.
- Peer: React >= 16.8 (hooks). Supports React 18 and 19.
- Storage backends: web storage (local/session), chrome extension storage,
  firefox (`browser.*`) storage, plus any user-supplied adapter.

## Layout

- `src/` — library source. Entry point `src/index.ts`.
  - `create-persisted-state.ts`, `create-async-persisted-state.ts` — the two hooks.
  - `src/storages/` — storage adapters. `src/utils/` — internals. `src/@types/` — public types.
- `__tests__/` — Jest tests, mirroring `src/`.
- `demo/` — Vite example app, not published.
- `lib/` — build output, generated by `tsc`. Never edit by hand.

## Style

Biome owns both linting and formatting; `biome.json` is authoritative, do not
hand-tune formatting against it. Two-space indent, single quotes, no semicolons,
trailing commas, 120 columns.

Naming follows role, not type. `camelCase` for variables, functions, methods and
properties; `PascalCase` for types, interfaces and components; booleans read as
predicates (`is`/`has`/`should`/`can`). A `use` prefix means the function is a
real React hook — never put it on a plain helper.

Comments explain **why**, never restate **what** the code already shows. If code
needs a comment to be understood, prefer fixing the naming or the structure. No
commented-out code, no changelog comments — that is what git is for. Document
public API with TSDoc on exports.

## Tests

Jest with ts-jest and React Testing Library, jsdom environment. Storage is
mocked via `jest-localstorage-mock` and `jest-webextension-mock`.

**A test must be proven able to fail.** Before a test counts as coverage, show it
red against the broken or unfixed code, then green after the fix. A test that
passes both before and after the change tests nothing and is worse than no test,
because it manufactures false confidence.

Watch for tests that lock in a bug as if it were the contract. This repository
has had them: cases asserting that `null` "is not saved" while the real defect
was that `null` is written to storage and then not read back. When behaviour
looks wrong, fix the behaviour and the test — do not enshrine the defect.

Tests must also exercise the real target. A suite that runs against the wrong
branch, wrong environment or wrong build proves nothing, however green it is.

## Commits and releases

Commit messages follow Conventional Commits, and this is load-bearing rather than
cosmetic: `@release-it/conventional-changelog` derives the released version and
the changelog directly from them. A wrong type means a wrong version.

`fix:` → patch, `feat:` → minor, `BREAKING CHANGE:` in the body → major. Also
used: `chore:`, `docs:`, `test:`, `refactor:`, `build:`, `ci:`.

Releases run from the **Release** workflow via `workflow_dispatch` — deliberately
manual, because dependency bots merge to `main` often and a push trigger would cut
a release for every one of those merges. Publishing uses npm OIDC trusted
publishing, so there is no npm token anywhere: never add `NODE_AUTH_TOKEN` to the
release workflow, as npm silently falls back to the legacy token path when it is set.

## Pinned versions, and why

Do not "helpfully" bump these; both were tried and reverted for concrete reasons.

- **TypeScript stays on 6.x.** TS 7 ships the Go compiler and drops the JS
  compiler API that ts-jest builds on. Blocked upstream until ts-jest supports
  TS 7.1.
- **`@vitejs/plugin-react` stays on 5.** v6 pulls an optional peer chain onto
  `@babel/core@8.0.0-rc`, which conflicts with the Babel 7 that Jest requires.
  Vite 8 documents that plugin v5 remains compatible.

No dependency `overrides`, no `--legacy-peer-deps`, no silencing flags. If an
upgrade does not resolve cleanly, the answer is to stay on the current version
and say why — not to patch the resolution. Such patches outlive the problem they
hide.

## Working rules

Research before changing. When something breaks or an upgrade fails, read the
official documentation, changelog and upstream issues first, then decide. Do not
fix by trial and error, and do not drift toward whichever option looks easier.

Behaviour-preserving refactors are verified by the existing suite staying green
before and after — they do not get a red-first test, since there is no behaviour
change to fail on.

Never discard uncommitted work. `git checkout --`, `git restore`, `git reset --hard`,
`git clean` and force pushes are off limits without an explicit instruction naming
the specific file.
